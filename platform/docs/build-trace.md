# Build trace

Append-only timing log written during `/build`. This is **not** task state —
that's `task-ledger.md`. This file exists purely so build/review time can be
measured and analyzed afterward (e.g. "how long did review cycle 2 take", "how
much of T03's time was rework").

Every row carries the task id **and** its title, so the trace reads standalone
without cross-referencing the ledger.

Who writes each step:
- `builder:*` rows — written by the **builder** (it has file-write access).
  Checkpoints: `start`, `context_read`, `file_written` (one row per file,
  detail = file path — **batched**: files finished in the same short burst
  share one `date` call and one `Edit`, not one round-trip each; see
  `builder.md`'s "Trace logging"), `tests_written`, `gates_start`,
  `gates_passed`, `submit_for_review`, `rework_complete`.
- `reviewer:*` rows — written by the **orchestrating session** immediately
  after a reviewer pass returns, since the reviewer agent is read-only by
  design (X1) and cannot write files itself. Step: `cycle_N` (N = cycle
  number), detail = a one-line finding summary (e.g. "2 BLOCKER, 1
  SHOULD-FIX" or "clear").
- `orchestrator:live_verification_start` / `orchestrator:live_verification_end`
  — written by the **orchestrating session** around any hands-on live
  verification it does itself (starting/restarting the preview server,
  browser-driven checks, seeding/cleaning temporary DB data, comparing
  against a wireframe screenshot). This work is real time that was
  previously invisible in the trace — it happened between a
  `submit_for_review`/`reviewer:cycle_N` row and whatever came next, with
  no record of how long it took. Log `_start` right before beginning this
  work and `_end` right after finishing it (whether it passed cleanly or,
  as in T07, surfaced a bug that then went through its own builder/reviewer
  cycle — in that case `_end` closes out the *verification* step; the bug
  fix itself gets its own `builder:*`/`reviewer:*` rows same as any other
  rework). Detail = a short note on what was checked and the outcome.
- `orchestrator:tokens` — written by the **orchestrating session** immediately
  after a builder call (initial build or a rework pass) returns, since the
  builder's own `submit_for_review`/`rework_complete` rows are written
  *during* its run, before the total token count for that call is known —
  only the orchestrator sees that number, and only after the call fully
  returns. Detail = which phase it closes out (`build` or `rework`), Tokens
  = that call's total. `reviewer:cycle_N` rows carry their own call's token
  total directly in the Tokens column instead of a separate row, since the
  orchestrator already writes those.
- `done` — written by the **orchestrating session** when the task clears.

**Tokens column**: populated by the orchestrator only, on `reviewer:cycle_N`
rows and `orchestrator:tokens` rows — the only two places a token total is
actually known at write time. Every other row leaves it blank. This is a
per-call total (the harness doesn't report finer granularity, e.g. tokens
spent on one file vs. another), so it answers "how many tokens did this
build/review/rework call cost," not "how many tokens did step X cost."

**Mechanical timestamp rule, no exceptions:** immediately before appending
a row or a batch of rows, run `date -u +"%Y-%m-%dT%H:%M:%SZ"` as its own
tool call and copy that exact output into the row(s). Never type a
timestamp from memory, pattern-match one from a nearby row, or estimate
elapsed time. T01 and T02's rows were written before this rule existed and
are known to be inaccurate (self-reported spans exceeded the actual measured
duration of the agent calls that produced them) — treat their absolute
durations as unreliable; T03 onward should be trustworthy. If you find an
out-of-order or implausible row, fix its timestamp rather than leaving it.
